# RouteSmith v0.4.0 — UX & Intelligence Overhaul

> **Status:** Design validated 2026-06-18
> **Target:** v0.4.0

## Goal

Make RouteSmith easier to start than OpenRouter's auto-router while being strictly smarter — per-agent learning, transparent explanations, proactive intelligence, zero-config operation. Every feature runs in-process with no data leaving the environment.

## Core Insight

OpenRouter is a **stateless gateway** with global routing (NotDiamond). RouteSmith is **stateful middleware** running in-process with per-agent bandit predictors. This asymmetry unlocks UX they literally cannot build: self-calibrating defaults, per-agent quality models, proactive recommendations, trust-but-verify, and auto-improving routing that gets smarter over time.

---

## Design Sections

### 1. Zero-Config Auto-Registration

**`RouteSmith.with_auto()`** — one call replaces all manual `register_model()` boilerplate.

```python
rs = RouteSmith.with_auto()
```

What it does:
- Discovers models from OpenRouter (if API key available) or LiteLLM curated list
- Fetches live pricing from OpenRouter/LiteLLM APIs
- Seeds cold-start quality scores from OpenRouter benchmark data (where available), defaults to 0.80 otherwise
- The bandit (LinTS/LinUCB) refines these within ~50 updates per agent
- Capabilities (vision, tool calling, context window) auto-populated from model metadata

Options:
```python
rs = RouteSmith.with_auto(include_all=True)          # all 200+ models
rs = RouteSmith.with_auto(providers=["anthropic", "openai"])  # filter
rs = RouteSmith.with_auto(seed_quality={"gpt-4o": 0.95})     # override seeds
```

**Why this beats OpenRouter:** They curate ~19 models. We auto-register 80-200. They can only route to models on their platform. We route to OpenRouter + Bedrock + Ollama + any LiteLLM provider.

### 2. Predictor-Aware Tradeoff Parameter

**`tradeoff` (0-10) acts as a multiplier on the bandit's reward function context.**

```python
rs.completion(messages=[...], tradeoff=7)
```

How it works:
- `tradeoff` is exposed in `reward_context.tradeoff` to custom reward functions
- Default behavior: scales `cost_lambda` linearly (0 = quality-only, 10 = max cost sensitivity)
- Custom reward functions interpret it freely (latency, safety, verbosity, etc.)
- Per-agent convergence means "7" auto-calibrates differently for your coder vs. your chitchat bot

**Why this beats OpenRouter:** Their slider is a static multiplier on NotDiamond's global routing scores. Ours is per-agent, adapts to your reward function, and improves over time.

### 3. Transparent, Explainable Routing

Every response includes `routesmith_explanation`:

```
Model used: gpt-4o-mini
Reason: cheapest model above quality threshold
Predicted quality: 0.89 ± 0.03 (94% confidence)
Models considered: 5  |  Qualified: 3  |  Rejected: 2
Cache: miss  |  Conversation: chat-abc-123 (turn 3)
```

Generated from existing `RoutingMetadata` + predictor diagnostics. No new data — just formatting.

**Why this beats OpenRouter:** They show which model. We show why.

### 4. Session-Sticky with KV Cache Awareness

**Session-level stickiness + cross-session exploration + hierarchical subagent IDs.**

```python
rs.completion(messages=..., conversation_id="main-chat-001")
```

- Within a session: the first call picks a model (bandit explores), subsequent calls stick to preserve KV cache
- KV cache switching cost is exposed to the reward function: `ctx.cache_status`, `ctx.estimated_cache_savings`
- Across sessions: each new conversation starts fresh KV cache → free exploration → bandit learns which initial model is best
- Subagents: `parent_conversation="main-chat-001"` creates hierarchical IDs, isolated sessions, parent learns from child outcomes

**Why this beats OpenRouter:** Their stickiness is binary (pin/don't pin). Ours is KV-cache-aware and feeds into the per-agent learning loop across sessions.

### 5. Auto-Sampling Quality Polls

**Callback-based injection with framework-adaptive rendering.**

```python
# RouteSmith generates poll metadata:
response.routesmith_poll = {
    "id": "abc123",
    "type": "numbered",
    "question": "How was this response?",
    "options": [
        {"id": 1, "label": "Good"},
        {"id": 2, "label": "Not good — wrong output"},
        {"id": 3, "label": "Not good — too slow"},
        {"id": 4, "label": "Not good — too expensive"},
        {"id": 5, "label": "Not good — too verbose"},
    ],
    "context": {"model": "gpt-4o-mini", "cost": "$0.0012"},
}

# Framework adapters render it:
config.on_poll = my_handler  # registered by adapter

# User answers:
rs.answer_poll("abc123", option=2)
# → predictor gets: quality=0.0, reason="quality_low"
# → adjusts quality_threshold upward for this agent
```

Sampling adapts to posterior uncertainty — new agents get polled more, converged agents less. Framework adapters (OpenClaw, LangChain, etc.) provide native rendering (thumbs up/down, numbered list, Slack buttons). When no callback registered, poll metadata is always available for manual inspection.

**Why this beats OpenRouter:** They get zero feedback after routing. We close the loop with per-agent preference signals.

### 7. Trust-but-Verify

**Shadow execution with automatic quality comparisons.**

```python
rs = RouteSmith.with_auto(verify_rate=0.05)

# 5% of requests run both cheap and expensive model, compare:
response.routesmith_verification = {
    "cheap_model": "gpt-4o-mini",
    "expensive_model": "gpt-4o",
    "equivalent": True,
    "summary": "gpt-4o added docstrings, functionally identical",
    "savings": "$0.012 (93%)",
}

# Cumulative trust per agent:
>>> rs.stats.verification("coder")
{"equivalence_rate": 0.94, "verified": 83}
```

**Why this beats OpenRouter:** Their claim of "60% savings" is marketing. Ours is verifiable in your own environment with your own data.

### 8. CLI Dashboard

```bash
$ routesmith stats           # snapshot, pipeable, --json flag
$ routesmith stats --watch   # live refresh
$ routesmith dashboard       # TUI (pip install routesmith[tui])
```

Both read from existing feedback storage (SQLite). No new data pipeline.

│  │ Engine            │                                       │

│  │ budget pacing     │  │ Framework Adapters               │  │
│  └──────────────────┘  │  poll rendering, injection        │  │
│                        └─────────────────────────────────┘  │
│  ┌──────────────────┐                                       │
